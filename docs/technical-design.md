# Contributor Community Platform — Technical Design v1

## 1. Architecture goals

- Keep the platform independent from the main omegaUp application while integrating cleanly with omegaUp and GitHub.
- Keep GitHub and omegaUp external calls out of user-facing HTTP request paths whenever synchronization is involved.
- Prefer boring, portable infrastructure for V1.
- Preserve clear authorization boundaries between contributor-visible and internal mentor/admin data.
- Make local development reproducible and friendly to open-source contributors.
- Avoid premature distributed infrastructure.

## 2. High-level architecture

```text
                  GitHub GraphQL
                       │
                       ▼
                 ┌───────────┐
omegaUp APIs ────►│   Worker  │
                 └─────┬─────┘
                       │
                       ▼
                PostgreSQL 17
                       ▲
                       │
                    FastAPI
                       ▲
                       │ REST / OpenAPI
                       ▼
                     Vue 3
```

GitHub and omegaUp synchronization is asynchronous. FastAPI reads local persisted state for normal page/API requests.

## 3. Backend

- Language: Python 3.13 (initial target)
- Framework: FastAPI
- Validation/API schemas: Pydantic
- API style: REST
- API contract/documentation: OpenAPI generated by FastAPI

Rationale: FastAPI provides typed request/response models and a clean OpenAPI contract without requiring a full-stack framework. Python remains a good fit for external integrations and background processing.

### Layering

Use pragmatic separation:

```text
API / routers
    ↓
services
    ↓
repositories / integrations
    ↓
SQLAlchemy / external clients
```

Avoid business logic and long-running external calls directly in route handlers.

## 4. Database and persistence

- Database: PostgreSQL 17
- ORM: SQLAlchemy 2.x
- Driver: psycopg 3
- Migrations: Alembic
- Initial DB access: synchronous SQLAlchemy sessions

Production schema evolution is performed through Alembic. `Base.metadata.create_all()` is not the production migration strategy.

Integration tests use real PostgreSQL, not SQLite, because the design may use PostgreSQL features such as JSONB, constraints, locking, and `FOR UPDATE SKIP LOCKED`.

### JSONB policy

Use relational tables for durable domain entities and relationships. Use JSONB for type-specific flexible configuration, validated through Pydantic models.

Example requirement configuration types may include:

- `OMEGAUP_TEST`
- `GITHUB_CONTRIBUTIONS`
- `VIDEO_REVIEW`

Do not turn the relational database into an unstructured document store.

## 5. Frontend

- Framework: Vue 3
- Language: TypeScript
- Build tool: Vite
- Architecture: SPA
- Routing: Vue Router
- Global state: Pinia, used selectively
- Component library: PrimeVue
- Styling/layout: Tailwind CSS
- SSR: not required initially

PrimeVue provides complex accessible components; Tailwind is used for layout, composition, responsive behavior, and product-specific visual identity.

Where useful, TypeScript API types/client code should be generated from the backend OpenAPI contract to reduce duplicated contracts.

## 6. Authentication and authorization

### Authentication

GitHub OAuth is the only initial login mechanism.

Flow:

```text
Browser → GitHub OAuth → FastAPI callback → Person/GitHub identity → server session
```

Use server-side sessions with secure cookies rather than storing application JWTs in browser `localStorage`.

Cookies should use appropriate `HttpOnly`, `Secure`, and `SameSite` settings in production. Mutable operations require appropriate CSRF protection.

### Authorization

Authentication answers "who are you?"; application data answers "what may you do?".

GitHub does not define application admin/mentor permissions.

Authorization is enforced by FastAPI. Frontend guards are UX only.

Mentor permissions should normally be scoped to relevant editions/programs. Platform administrators are separate from transient edition mentor roles.

Internal evaluation/ranking endpoints and response schemas must be isolated from contributor-facing APIs.

## 7. GitHub integration

- External API: GitHub GraphQL
- Synchronization: dedicated Python worker
- Local data: partial reconstructible replica
- Repository selection: administrator-controlled
- Initial repository: `omegaup/omegaup`

Normal HTTP requests never perform GitHub synchronization.

### Sync modes

- Incremental synchronization for normal operation.
- Full rebuild for administrative recovery/reconstruction.

Synchronization is paginated and rate-limit aware.

Potential replicated entities include users, issues, pull requests, labels, reviews, milestones, and relationships required by product workflows.

GitHub remains authoritative. A PR is considered completed only when GitHub reports it merged.

### Credentials

GitHub OAuth credentials are distinct from worker integration credentials.

V1 may use a service PAT/configured integration token for synchronization. A GitHub App is the preferred future organization-level integration when the project moves under omegaUp.

## 8. omegaUp integration

omegaUp remains authoritative for contest/test progress.

### Identity verification

A contributor may temporarily provide an omegaUp API token. The backend calls omegaUp's authenticated current-session API, derives the actual username, stores the verified identity association, and discards the personal token.

Personal omegaUp API tokens must never be persisted or logged.

### Test synchronization

Edition configuration includes at least:

- contest alias
- scoreboard URL
- minimum distinct solved problems
- manual-approval behavior

The worker uses omegaUp scoreboard data for current progress and `scoreboardEvents` for the event timeline. From events, it derives the timestamp at which the Nth distinct problem first received AC.

Only a small progress projection is stored locally; the platform does not mirror omegaUp generally.

Integration failure should leave stale-but-visible local progress rather than making the WebApp unavailable.

## 9. Background jobs and scheduling

V1 deliberately avoids Celery, Redis, and RabbitMQ.

- Queue: PostgreSQL-backed jobs table
- Worker: Python process using the backend codebase/image
- Scheduler: APScheduler
- Claiming/locking: PostgreSQL transactions with `FOR UPDATE SKIP LOCKED`
- Payloads: JSONB where appropriate
- Retries: bounded exponential backoff
- History: persistent

Conceptual job states:

```text
PENDING → RUNNING → SUCCEEDED
              └──→ RETRY → PENDING
              └──→ FAILED
```

Manual and scheduled synchronization use the same queue path. HTTP endpoints enqueue work and return `202 Accepted`; they do not perform the work inline.

Scheduling configuration belongs to persisted product/integration configuration where per-edition/per-source variation is needed.

Workers must recover safely from abandoned `RUNNING` jobs after crashes/restarts, subject to job idempotency rules.

## 10. Configuration and secrets

This area remains partially open and should be finalized before production deployment.

Current direction:

- Deployment configuration: environment variables.
- Product/program/edition configuration: PostgreSQL.
- Flexible typed configuration: JSONB + Pydantic validation.
- Contributor omegaUp API token: ephemeral; never stored.
- Secrets must never appear in logs or API responses.

omegaUp production already uses SOPS for infrastructure secrets; the final boundary between SOPS-managed deployment secrets and encrypted runtime/product secrets should be resolved when production deployment is designed. This is not a blocker for Milestone 1.

`.env.example` is committed with safe placeholders. Real `.env` files are not committed.

## 11. Testing strategy

Principle: many fast deterministic tests, real integration tests where infrastructure semantics matter, and a small high-value E2E suite.

### Backend

- pytest
- pytest-cov
- unit tests for business rules
- API authorization tests
- PostgreSQL integration tests
- Alembic migration tests

### External APIs

Normal tests do not call production GitHub or omegaUp.

Use realistic stored fixtures and HTTP mocks for deterministic tests. Periodic/manual/nightly contract tests may verify that GitHub and omegaUp response contracts still match expectations.

### Frontend

- Vitest
- Vue Test Utils

Focus on meaningful behavior, stores/composables, permissions, and workflow components rather than DOM trivia.

### E2E

- Playwright
- small set of critical contributor/mentor/admin workflows
- deterministic test authentication instead of real GitHub OAuth in E2E

Flaky required tests are treated as test bugs. Do not normalize repeated retries until green.

## 13. Health and observability

### Health

- `/health/live` — process liveness
- `/health/ready` — readiness, including required local dependencies such as PostgreSQL

GitHub/omegaUp availability does not determine WebApp readiness.

### Logging

- structured logging
- JSON to stdout/stderr in production
- human-friendly development formatting
- request IDs and job IDs for correlation
- no authorization headers, cookies, API tokens, secrets, or password-bearing DB URLs

### Metrics/tracing

Design for OpenTelemetry compatibility rather than embedding vendor-specific New Relic calls throughout application code.

Initial useful signals include HTTP latency/error counts, job queue state, job duration/retries, integration sync duration/failures, rate-limit state, and last-successful-sync age.

### Operational UI

Admin-facing system status may expose integration freshness, job queue state, and recent failures. This is distinct from infrastructure healthchecks and from product audit history.

### Audit trail

Audit records are durable product data in PostgreSQL and are distinct from operational logs.

## 16. Deployment roadmap

1. Local Docker development.
2. V1 deployed entirely on personal VPS, including PostgreSQL.
3. Optional migration of PostgreSQL to Neon Free when useful.
4. Demonstrate working application and propose `community.omegaup.com`.
5. If approved, evaluate Neon Open Source Program and omegaUp production hosting in parallel.

Avoid hardcoding personal domains, usernames, filesystem paths, or repository owners. Deployment-specific values belong in configuration.

## 17. Architectural guardrails

- Never perform GitHub or omegaUp synchronization synchronously inside normal HTTP requests.
- Never expose internal evaluations/rankings through contributor APIs.
- Never persist contributor omegaUp API tokens.
- GitHub replica data must remain reconstructible.
- GitHub is authoritative for GitHub contribution state.
- omegaUp is authoritative for omegaUp test state.
- All production schema changes use Alembic.
- Do not introduce Redis/RabbitMQ/Celery without a demonstrated need and explicit architectural decision.
- New business rules require tests.
- Do not bypass failing tests to finish a task.

## 18. GitHub repository-permission verification for mentor eligibility (proposed, not implemented)

Product requirement: a future "request mentor" action (the eligible-user
request/approval workflow in `docs/feature-backlog.md`, item 9) must be offered
only to users with sufficient permissions on `omegaup/omegaup` (provisionally
GitHub `Triage` or higher — subject to product confirmation). See product-design
§23. The initial mentor capability (milestone issue M1-07b) is direct superadmin
assignment and does not depend on this verification. This section proposes a
least-privilege verification strategy for that future workflow. **Nothing here
is implemented, and no API contract is assumed.**

### 18.1 Why current scopes are insufficient

The OAuth login scope is `read:user` (technical-design §6, M1-06). It yields the
authenticated user's profile only. It does **not** expose the user's permission
level on any repository. Repository-permission data requires either a different
OAuth scope or a GitHub App installation. We must not infer permissions from
`read:user`.

### 18.2 Candidate approaches (least-privilege first)

Options, roughly from least to most privilege/complexity:

1. **GitHub App installed on the omegaUp org (preferred long-term).**
   - A GitHub App installed on `omegaup/omegaup` can read collaborator
     permission levels via the installation token, without each user granting
     broad personal scopes.
   - Aligns with technical-design §7 ("A GitHub App is the preferred future
     organization-level integration when the project moves under omegaUp").
   - The permission check (`GET /repos/omegaup/omegaup/collaborators/{login}/permission`
     or the GraphQL equivalent) runs server-side with the App token and returns
     a role such as `read` / `triage` / `write` / `maintain` / `admin`.
   - Least-privilege for the *user*: no extra user scope needed; the user only
     needs their verified GitHub identity (already established at login).

2. **Short-lived elevated OAuth authorization, consumed once.**
   - At the moment a user attempts to request mentorship, perform a separate,
     explicit OAuth authorization requesting a narrow scope sufficient to read
     the user's own repository permission, then discard the token.
   - More user-facing friction and a broader user grant than option 1; keep only
     as a fallback if a GitHub App is not yet available.

3. **Admin-attested eligibility (no GitHub call).**
   - A superadmin records that a user meets the threshold out-of-band.
   - Always available regardless of integration status; useful as a manual
     escape hatch and for development/testing.

### 18.3 Design constraints

- **Verification is asynchronous and cached**, consistent with the "no external
  sync in request paths" guardrail (§17). The permission check runs out of band
  (a job) or at an explicit user action, and its result is persisted as a
  short-lived, reconstructible eligibility projection with a checked-at
  timestamp — not re-fetched on every page load.
- **Eligibility ≠ role.** A positive permission check only makes the request
  action available; it never auto-grants mentor status. A superadmin still
  approves (product-design §23.2).
- **Fail closed.** If permission cannot be verified (integration down, user not
  a collaborator), the request action is simply not offered; no implicit grant.
- **Store the minimum.** Persist the derived eligibility decision and the
  permission level observed, not GitHub tokens. Never persist an App
  installation token or a user token beyond its immediate use.
- **Provenance of the threshold.** The `Triage`-or-higher threshold is a
  configurable product decision, not a hardcoded constant buried in code.

### 18.4 Open questions

- Is a GitHub App available/approved for `omegaup/omegaup` in the M1 timeframe,
  or must M1-07b rely on admin-attested eligibility (option 3) initially?
- Exact threshold mapping (does `maintain`/`admin` imply eligibility; is
  `write` sufficient, or strictly `triage`+?).
- How stale may a cached eligibility result be before re-verification?

## 19. omegaUp GSoC ideas/editions synchronization (proposed, not implemented)

Supports product-design §21. **Not implemented; no omegaUp API contract is
assumed.** Recorded so later models remain compatible.

- Treat omegaUp ideas/editions as an **incremental, reconstructible projection**
  persisted locally (same pattern as the GitHub replica, §7). Normal requests
  read local state; the omegaUp API is never required to be online to render a
  page.
- Synchronization runs through the existing PostgreSQL-backed job queue and
  worker (§9), never inside a request handler (§17).
- Preserve **stable omegaUp identifiers** (idea id, edition id) on the local
  projection so it can be dropped and rebuilt.
- Keep a strict boundary between **omegaUp-owned fields** (idea/edition editorial
  content and publication state) and **Community-owned fields** (links to
  Community identities, mentors, applications, participants, internal
  review/evaluation state). The projection stores omegaUp-owned fields as a
  cache; Community-owned relationships reference the projection by stable id.
- The Edition model needs a **source/provenance** attribute (Community-managed
  vs. omegaUp-projected) and an optional external id. Community-native editions
  (internships, residencies, volunteer) must not require omegaUp connectivity.
